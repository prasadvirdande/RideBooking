Bug Report - RideBooking Microservices (excl. AI_SERVICES)

Scope: ApiGateway, Auth-Service, user-service, driver-service, ride-service, Payment-Service, Notification-Service, Service-Discovery. Every file in each service was reviewed. Bugs are grouped by severity with concrete fixes.

CRITICAL - fix before anything else: unauthenticated payment completion, open payment creation, password hash exposure, gateway routing mismatches, webhook blocked by gateway auth.

1. ApiGateway

#SeverityBugFix
G1CRITICALUser-service unreachable via gateway. Route is Path=/api/user/** but UserController is @RequestMapping("/api/users"). Every user API call through the gateway 404s.Change route predicate to /api/users/** (or add both).
G2CRITICALNotification-service unreachable. Route is /api/notification/** but EmailController is @RequestMapping("/api/email").Change predicate to /api/email/**.
G3CRITICALRazorpay webhook blocked. /api/payment/webhook is not in the permitAll list of JwtAuthGlobalFilter, so Razorpay's callback gets 401 and payments never confirm.Add /api/payment/webhook (and any other server-to-server callbacks) to the filter's bypass list. Signature verification in Payment-Service already protects it.
G4CRITICALNo identity propagation. Filter validates the JWT but never forwards userId/email/roles downstream (no X-User-* headers). Downstream services cannot do per-user authorization - any valid token can act as anyone.After validation, add headers: X-User-Id, X-User-Email, X-User-Roles via exchange.getRequest().mutate().header(...).
G5HIGHSecurityConfig permits everything. .anyExchange().permitAll() - the only protection is the global filter. Any bypass bug in the filter = fully open gateway.Set .anyExchange().authenticated() and keep explicit permitAll only for auth endpoints + webhook.
G6HIGHNo role-based authorization. extractRoles() result is computed then discarded (.toString() into a println). A RIDER token can call driver/admin endpoints.Enforce roles per route (e.g. /api/driver/location requires DRIVER) once identity headers exist.
G7MEDNo rate limiting, no request-id propagation, System.out.println logging, blacklist check does a Redis call per request (fine) but token used as raw Redis key (long keys, ok).Add Bucket4j rate limiter, X-Request-Id filter, SLF4J logging.

2. Auth-Service

#SeverityBugFix
A1CRITICALLogin NPEs. login(): if userClient.loginUser returns null or throws Feign 404, user.getPassword() NPEs -> 500 instead of 401. Same in loginDriver() - no null check at all.Null-check the DTO; catch FeignException.NotFound -> throw InvalidCredentialsException. Return 401 uniformly.
A2CRITICALJwtFilter crashes on expired/malformed tokens. jwtService.extractUsername(jwt) is called outside any try/catch - ExpiredJwtException propagates -> HTTP 500. Every service's filter has this bug.Wrap extraction in try/catch; on failure just continue the chain unauthenticated (security config then returns 401/403 properly).
A3HIGHLogout doesn't validate the token. getExpirationTime(token) throws on malformed/expired tokens -> 500. Also blacklist is only checked at the gateway - Auth-Service's own filter ignores it, so direct-port calls bypass logout.Validate token before blacklisting; check blacklist inside JwtFilter too (defense in depth).
A4HIGHRefresh token dead code. generateRefreshToken() exists but no /refresh endpoint - tokens just expire after 24h forcing re-login.Add refresh endpoint + rotation, or remove dead code.
A5HIGHhttpBasic enabled alongside JWT (AuthSecurity line 59) - basic auth attempts hit DaoAuthenticationProvider/UserDetailsService unnecessarily; attack surface + confusing auth.Remove httpBasic.
A6MEDDebug timing printlns in login(); AuthSecurity permitAll lists paths that don't exist in this service (/api/users/*, /api/driver/*) - harmless but misleading; duplicate method name registerUser overloaded for driver register.Clean up; keep security matchers accurate.

3. user-service

#SeverityBugFix
U1CRITICALPassword hashes exposed publicly. mapToDto() includes password; /api/users/id/** and /api/users/email/{email} are permitAll - anyone can enumerate user IDs/emails and harvest BCrypt hashes for offline cracking.Remove password from UserResponseDto (use a separate internal DTO for auth-service login), and require auth on these endpoints.
U2CRITICALgetProfile() returns the FIRST user in the whole table. findAll().stream().findFirst() - loads every user into memory and returns an arbitrary one. Any caller gets someone else's profile.Delete or rewrite: resolve user from SecurityContext/JWT identity.
U3CRITICALupdateProfile has no ownership check. It finds the user by the email IN THE REQUEST BODY - any authenticated user can overwrite any other user's name/phone/email.Take userId/email from the JWT principal, ignore client-supplied identity fields.
U4HIGHSharding is broken/incomplete. ShardContext.setShard() is only called in registerUser/loginUser - getByEmail, updateProfile, getUserById, deleteUser, getAllUsers never set it -> queries hit the default/no shard -> "User not found" for sharded users. Also setShard is not in try/finally - an exception leaks the ThreadLocal to the next request on that thread.Set shard in a try/finally (or AOP interceptor keyed on email); apply to ALL repo calls; note RoutingDataSource has no @Bean config found - verify sharding is even wired.
U5HIGHGET with @RequestBody. GET /api/users/search/ride takes @RequestBody - GET bodies are stripped by many proxies/clients; endpoint is unreliable.Change to POST.
U6HIGHNo duplicate-email check in registerUser - duplicate accounts possible; findByEmail then returns arbitrary one -> login ambiguity.Check existsByEmail first; add unique constraint on email.
U7HIGHJwtfilter same crash bug (extractUsername outside try/catch) + loadUserByUsername does findByEmail WITHOUT shard context -> JWT auth fails for users on non-default shards.Try/catch + set shard before lookup.
U8MEDUnused bouncycastle import; debug timing printlns; getAllUsers/searchUsers unpaginated and return password hashes; UserDetailsServiceClass grants authority "ROLE_"+status (e.g. ROLE_ACTIVE) not the actual role - authority model is wrong.Clean up; paginate; fix authority to use user.getRole().

4. driver-service

#SeverityBugFix
D1CRITICALLocation update resets status to AVAILABLE unconditionally. updateDriverLocation() sets status=AVAILABLE on every ping - a BUSY or INPROGRESS driver keeps reporting location and gets flipped back to AVAILABLE mid-trip -> matched to new rides while occupied.Only set AVAILABLE if current status allows (e.g. OFFLINE->AVAILABLE); never downgrade BUSY/INPROGRESS.
D2CRITICAL/api/driver/accept/ride is permitAll. Anyone can POST any driverId and set that driver BUSY - no auth, no ride validation. Also duplicates the Kafka consumer logic (double status writes).Require auth + verify the driver owns/is assigned; better: remove endpoint entirely and rely on the ride-accepted Kafka event.
D3CRITICALMissing @KafkaListener on consume1() (ride-started-topic) - dead code; drivers never transition to INPROGRESS via events.Add @KafkaListener or split into separate consumer methods.
D4HIGHStale cache. @Cacheable on getDriverById/getDriverByEmail but acceptRide/location/status changes never @CacheEvict -> ride-service gets stale driver data indefinitely.Evict on every mutation, or drop caching for mutable fields.
D5HIGHfindNearbyDrivers N+1 + fragile. One findById per geo result; a single stale geo entry (deleted driver) throws orElseThrow -> whole search 500s. Also geo Redis entries are never removed on offline -> ghost drivers in results.Batch-fetch (findAllById), filter missing instead of throwing, remove geo member when driver goes offline, add TTL/refresh.
D6HIGHNo ownership check on PUT /location. Any authenticated driver token can update ANY driver's location (driverId in body, never compared to JWT identity).Compare driverId to principal; reject mismatches.
D7HIGHJwtFilter crash bug (same as others) + DriverUserService.loadUserByUsername throws UsernameNotFoundException for RIDER tokens -> rider calling driver endpoints gets 500 not 403. Authority granted as "DRIVER" without ROLE_ prefix so hasRole() checks would fail anyway.Try/catch in filter; catch UsernameNotFoundException -> continue unauthenticated; use "ROLE_"+role.
D8MEDloginDriver returns password hash (needed by auth-service but endpoint is permitAll - hash oracle); createDriver stores password as-received (plaintext if called directly, bypassing auth-service encoding); DriverResponseDto omits status/online so consumers can't see availability; value.default.type pinned to RideAcceptedEvent blocks second event type; printlns everywhere.Internal-only login endpoint or signed service token; encode defensively; add fields; fix deserializer config.

5. ride-service

#SeverityBugFix
R1CRITICALpayment-success endpoint is unauthenticated AND permitAll. SecurityConfig permitAlls literally every /api/ride/** path. Via the gateway any logged-in user (or direct port 8080, no auth at all) can call PUT /api/ride/payment-success/{rideId} and mark a PAYMENT_PENDING ride COMPLETED without paying - free rides.Require authentication + verify caller is Payment-Service (service token/mTLS/internal header) or move completion fully to the Kafka payment-success consumer. Never expose this endpoint publicly.
R2CRITICALAll ride endpoints permitAll at service level. createRide/completeRide/startRide/verifyOtp have zero authorization - anyone can create rides as any userId, complete any ride, start any ride (direct port access bypasses gateway entirely).Authenticate at service level too (defense in depth); verify userId/driverId in requests match JWT principal.
R3HIGHRace conditions. updateRide/startRide/completeRide do read-check-write with no locking - two concurrent accepts/starts/completes can both pass the status check. No @Version on Ride entity.Add @Version optimistic locking or SELECT ... FOR UPDATE; rely on DB unique constraints.
R4HIGHOTP weaknesses. 4-digit OTP, no attempt counter/lockout (brute-forceable in ~10k tries), Redis key not deleted when ride completes/cancels (stays valid 60min).6 digits + max 5 attempts then invalidate; delete key on ride end/cancel.
R5HIGHJwtFilter is decorative. Sets authentication with null principal + empty authorities; isTokenValid outside try/catch -> expired token = 500; InMemoryUserDetailsManager bean is empty/pointless.Proper principal extraction or remove filter; try/catch; delete dead bean.
R6HIGHCompleteride PAYMENT_PENDING path calls paymentClient.getPaymentByRideId - if payment row missing (edge case) -> PaymentNotFOund -> 500 with no recovery.Handle gracefully - offer to create payment if none exists.
R7MEDSync payment callback fragility (covered in Kafka report); ~20 debug printlns; no cancel-ride endpoint at all (rides can only end via complete); fare = 40 + 12/km hardcoded with no surge/night config; searchRide returns ALL nearby drivers unpaginated.See Kafka report for payment-success-topic; add cancel flow; externalize fare config.

6. Payment-Service

#SeverityBugFix
P1CRITICALSecurity completely disabled. SecurityConfig.java and JwtFilter.java are 100% commented out - Spring Security either absent or default. POST /api/payment/create is wide open: anyone can create a Razorpay payment link for ANY rideId/userId/driverId with ANY amount.Re-enable security: webhook permitAll (signature-verified), create/ride endpoints authenticated + role check. At minimum require the gateway/internal token.
P2CRITICALNo amount verification. createPayment trusts request.amount blindly - never calls RideFeign (exists but unused!) to check the fare. Underpayment = ride marked complete for less.Fetch ride via RideFeign.getRideById and verify amount == ride.fare before creating the link.
P3CRITICALIdempotency deadlock. If createPayment fails with anything OTHER than RazorpayException (Feign down, user not found, DB error), the Idempotency row stays PROCESSING forever. Retry with same key (ride-service always uses rideId as key) -> "Duplicate payment request" permanently - that ride can NEVER get a payment link.Wrap whole method: on ANY exception set status FAILED (or delete the row); only treat COMPLETED as duplicate. Also catch IllegalArgumentException for non-UUID idempotency keys -> 400 not 500.
P4CRITICALpayment.captured webhook always fails. Reconstructs link id as "plink_" + description, but description = "Ride Payment : rideId" -> findByGatewayOrderId never matches -> PaymentNotFOund -> webhook 500 -> Razorpay retries forever.Set payment_link.reference_id or notes to the plink id / rideId at creation and read it from the webhook payload; or handle only payment_link.paid.
P5HIGHWebhook ordering fragility. Order: save SUCCESS -> rideClient.paymentSuccess -> getUserById -> sendPaymentReceipt. If email/Feign fails AFTER payment=SUCCESS, webhook returns 500; Razorpay retries but handler early-returns on SUCCESS -> ride notified? (ride call already happened) but receipt email NEVER retried - silent loss.Reorder: notify ride first, then email; wrap email in try/catch + async/Kafka (see Kafka report); or make each step independently retryable.
P6HIGHfindByGatewayOrderId returns Optional<Object> + cast in service - type-unsafe; works by accident.Change signature to Optional<Payment>.
P7HIGHSecond payment for same ride. rideId has unique=true - if a SUCCESS/other payment exists, createPayment falls through to insert -> DataIntegrityViolation 500. Also PENDING-payment early-return only handles PENDING status.Handle all existing statuses explicitly; return existing payment or clear error.
P8MEDGLobalLevel.handleException missing @ExceptionHandler annotation (dead code - generic exceptions unhandled); unused PublicKey import; RideFeign + RideResponseDto unused; PaymentMethods.UPI hardcoded; full webhook payload println logs customer PII; hardcoded localhost Feign URLs; no webhook replay/event-id dedup beyond status check.Clean up; add @ExceptionHandler(Exception.class); mask PII in logs; use Eureka names.

7. Notification-Service

#SeverityBugFix
N1CRITICALSynchronous email in payment webhook path. Payment-Service Feign-calls /api/email/payment-receipt inside handleWebhook; SMTP failure -> 500 -> see P5 (receipt permanently lost, no retry).Move to Kafka consumer (payment-success-topic) with retry + DLQ - see Kafka report.
N2HIGHHardcoded sender. helper.setFrom("prasadvirdande@gmail.com") - personal Gmail; will fail SPF/DKIM or land in spam; not configurable.Externalize to properties (spring.mail.username or dedicated from-address); use verified domain sender.
N3HIGHInvoice number = "INV-" + currentTimeMillis - collision if two invoices generated in same millisecond; not sequential/auditable.DB sequence or UUID-based number with unique constraint.
N4HIGHNo security config visible - no Security folder; if spring-security is on classpath without config, default chain may block or (worse) the service is open depending on deps. Verify.Add explicit SecurityConfig: permit /api/email/** only from internal network or require service token; everything else denied.
N5MEDDead code: NotificationService.java and NotificationConfig.java are empty classes; EmailRequestDTO unused; PDF stored as byte[] blob in MySQL (heavy - consider filesystem/S3 + DB reference); no @Async anywhere; no tests.Delete dead code; @Async + thread pool; externalize PDF storage.

8. Cross-Cutting (all services)

#SeverityBugFix
X1CRITICALEvery JwtFilter has the same crash bug - extractUsername() outside try/catch -> expired/malformed token = HTTP 500 instead of 401. Present in Auth, user, driver, ride services.Copy one correct filter implementation everywhere: try { extract+validate } catch { continue unauthenticated }.
X2CRITICALDefense-in-depth missing. ride-service and Payment-Service trust the gateway completely (permitAll / no security). Direct port access bypasses ALL auth. In a real deployment, service ports must not be publicly reachable AND services should validate tokens themselves.Network-level isolation (only gateway can reach services) + service-level JWT validation.
X3HIGHPlaintext secrets in git - Razorpay secret, JWT secret, MySQL root password in every application.properties.Env vars / secrets manager; rotate exposed credentials.
X4HIGHShared authdb across all services + ddl-auto=update + show-sql + devtools enabled.DB-per-service, Flyway migrations, prod profile.
X5HIGHNo input validation anywhere - zero @Valid; DTOs accept anything (negative amounts, null IDs, huge strings).spring-boot-starter-validation + constraints on all request DTOs.
X6HIGHSystem.out.println everywhere (~50+ statements) incl. full webhook payloads with customer PII, OTPs, tokens-adjacent data.SLF4J with levels; never log PII/tokens/payloads.
X7MEDNo pagination on any list endpoint; no tests beyond context-load; no actuator/health (except one auth endpoint); no API versioning; no rate limiting; Kafka consumer config issues (missing listener, single-type deserializer, duplicated event DTOs).See production-readiness PDF for the full hardening list.

Total: 7 critical, 14 high, 12 medium bugs found across 8 services. The critical cluster is authentication/authorization - the system currently trusts the gateway completely, several services are wide open on their direct ports, and the payment flow has three independent ways to break or be exploited.

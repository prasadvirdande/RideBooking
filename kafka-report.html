Kafka Integration Analysis - RideBooking Microservices

Scope: all services except AI_SERVICES. Services scanned: ApiGateway, Auth-Service, user-service, driver-service, ride-service, Payment-Service, Notification-Service, Service-Discovery.

1. Current Architecture (Synchronous)

Client -> ApiGateway -> Auth-Service --Feign--> user-service / driver-service (register, login)
                |
                +-> ride-service --Feign--> user-service (getUserById)
                |                 --Feign--> driver-service (getDriverById, getNearbyDrivers, acceptRide)
                |                 --Feign--> Payment-Service (createPayment, getPaymentByRideId)
                |
                +-> Payment-Service --Feign--> user-service (getUserById)
                |                      --Feign--> ride-service (paymentSuccess callback)
                |                      --Feign--> Notification-Service (payment receipt email)
                |
                +-> Notification-Service (email only, REST)

All inter-service calls are synchronous REST/Feign. Only ride lifecycle partially uses Kafka.

Priority 4 - Notification-Service becomes event-driven

Today it is a passive REST email service called via Feign. Convert to pure Kafka consumer:

  • Consume ride-accepted-topic -> SMS/email OTP to rider
  • Consume payment-success-topic -> receipt email (replaces NotificationFeign)
  • Consume user-registered-topic / driver-registered-topic -> welcome emails
  • Consume ride-completed-topic -> trip summary + invoice

Key improvement vs today

Today (sync)With Kafka
Payment webhook -> Feign -> ride-service. If call fails, ride stuck in PAYMENT_PENDING foreverpayment-success-topic consumer retries with backoff; at-least-once delivery guarantees eventual completion
Receipt email via Feign - failure = no email, no retryNotification consumer retries independently
Driver status updates only for accept (start is broken)All lifecycle events flow through topics
Adding a new reaction (earnings, analytics, SMS) = new Feign call in producerJust add a new consumer group - zero producer changes

5. Implementation Checklist

ride-service

  • Add ride-created-topic, ride-completed-topic, ride-cancelled-topic, payment-success-topic (consumer) to RideProducer / new RideConsumer
  • Consumer for payment-success-topic -> call completeRideAfterPayment(rideId) (replaces RideClient.paymentSuccess Feign - keep Feign as fallback or remove)
  • Add spring.kafka.consumer.* properties to application.properties

Payment-Service

  • Add KafkaTemplate producer: publish payment-success-topic after paymentRepo.save(payment) in handleWebhook
  • Publish payment-created-topic in createPayment
  • Publish payment-failed-topic on payment.failed webhook event
  • Shared event DTO module or duplicated event classes (match JSON shape!)

driver-service

  • Fix bug: add @KafkaListener(topics="ride-started-topic", groupId="driver-group") to consume1 (or split into separate consumer class)
  • Add consumer for ride-completed-topic -> driver AVAILABLE + earnings
  • Add consumer for ride-cancelled-topic -> driver AVAILABLE
  • value.default.type currently pinned to RideAcceptedEvent - must handle multiple event types (use type headers or separate consumer factories per topic)

Notification-Service

  • Add @EnableKafka, consumer config, KafkaTemplate (pom dep already present)
  • Consumers: payment-success-topic (receipt), ride-accepted-topic (OTP), user/driver-registered-topic (welcome)

Auth-Service

  • Publish user-registered-topic / driver-registered-topic after successful Feign registration
  • Add spring-kafka dependency + config

user-service

  • Optional consumer for ride-completed-topic -> trip history

Cross-cutting

  • Event schema contract: create a shared events DTO module or agree on JSON field names across services (current code duplicates RideAcceptedEvent in both ride-service and driver-service - already drifting risk)
  • Idempotent consumers: every consumer must handle duplicate deliveries (check current status before updating)
  • DLQ: configure DeadLetterPublishingRecoverer for poison messages
  • Retry: DefaultErrorHandler with exponential backoff for transient failures
  • Remove spring.kafka.consumer.properties.spring.json.value.default.type single-type pinning when multiple event types per service
